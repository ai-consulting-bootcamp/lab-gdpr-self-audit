# Data Processing Brief: Interview Prep Report

**For:** Data Protection Officer
**From:** Julia Antunes
**Date:** 17 Nov 2026

**System:** Interview Prep Report, an n8n-based workflow for job seekers. Candidates enter a company name, paste a job description, and provide at least one candidate source (PDF CV and/or public GitHub profile). The system researches the company, checks the job against the candidate evidence, and displays a tailored interview-preparation report. Invalid submissions may also be logged to a Notion page.

## 1. What personal data does the system process?

The workflow collects the information that a candidate enters and the data generated while processing it. In some cases, this can include personal information about the candidate or their work history.

| Data | Detail |
|---|---|
| **Company name** | Provided by the user as the target employer. |
| **Job description** (free text) | Full pasted job posting text. Can contain company-specific details, role requirements, and other information from a third party. |
| **Candidate CV** | Uploaded PDF file; text is extracted and used as candidate evidence. A CV may contain names, contact details, work experience, projects, education and other personal details. |
| **GitHub profile / username** | Optional public profile URL or username supplied by the user. This may reveal the candidate's public coding activity and project history. |
| **Public GitHub repository data** | Repository metadata and README content from public, non-fork repos, retrieved through the GitHub API. This can include project descriptions, technical details and personal/portfolio information shared publicly. |
| **Company research data** | Company background, recent news and web results from Tavily and GNews, based on the company + role. This may include publicly available company information and news items. |
| **Generated report output** | AI-generated content such as company background, role requirements, fit summary, project highlights, skill gaps, and likely interview questions. These sections can reflect the job description and candidate evidence. |
| **Validation results** | The workflow validates the report and candidate evidence. It may remove unsupported claims and retain validation metadata, including error messages. |
| **Validation-error records** | If the Notion logging branch is enabled, invalid submissions may be recorded in a Notion page, including the form error and related submission data. |
| **Technical data** | IP addresses, request metadata and execution logs generated by n8n, the browser form and external services. |

## 2. Where does the data come from?

From **job seekers directly** (company name, job description, CV upload, GitHub profile URL/username, form submissions), **public third-party sources** (company pages, recent news, public GitHub repositories and README files), **generated by the AI model** (company background, skill gaps, interview questions, validation output), and **optional internal logging** (Notion page for validation errors). No HR, applicant-tracking system, customer database, or protected employee database is connected to this workflow.

## 3. What is the data used for?

(1) Building the interview-preparation report, including company background, relevant news, likely interview questions and skill gaps. (2) Comparing the job description against the candidate's CV and GitHub evidence. (3) Validating that the generated report includes the required sections and that claims are supported by evidence. (4) Allowing the user to review the result in the form. (5) Logging invalid submissions when the Notion branch is enabled. (6) Detecting and fixing workflow or validation issues. (7) Keeping a single user session active while the workflow runs.

## 4. Who processes it, and where?

| Service | Role | What it receives | Location |
|---|---|---|---|
| n8n (Cloud or self-hosted) | Orchestrates the workflow and displays the form/report | All entered data, CV text, GitHub data, generated report, execution history and validation errors | Depends on deployment; no EU region is specified in the project documentation |
| OpenAI | Generates the structured interview-preparation report and validates report content against evidence | Company name, job description, CV text, GitHub data, company research results, generated report draft | US |
| Tavily | Researches the company and role context | Search query created from the company and job details | US |
| GNews | Retrieves recent company news items | Company name and short topic query | Not documented |
| GitHub REST API | Retrieves public repository metadata and README content | GitHub profile or username and public repository data requests | US |
| Notion (optional) | Logs validation errors for invalid submissions | Invalid submission details, error messages and related metadata when enabled | US |
| Browser / hosting environment | Receives submitted form data in transit and stores request metadata | Form input, upload content and request logs | Deployment-dependent |

The project is built with free or trial integrations, and the README does not document formal data-processing agreements or retention settings for the external services. The workflow does not currently persist generated reports in a dedicated database, but the form and execution logs may still retain operational records depending on n8n and connected services.

## 5. Does the system make or assist decisions that affect people?

It does not make employment or hiring decisions. It helps the job seeker prepare for interviews by generating a report based on the company, the role and the candidate's own evidence. The system does not automatically approve, reject or rank the person; it mainly supports interview preparation.

It does, however, produce generated outputs that can influence how the candidate prepares and what they emphasize in an interview. It also validates the report and removes unsupported candidate claims, which creates a quality-control layer but not a decision on suitability for employment. There is no human review before the report is displayed to the user. Invalid submissions are rejected by form validation, which is a process rule rather than an individual decision-making function.
