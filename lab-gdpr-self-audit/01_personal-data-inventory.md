## Purpose-compatibility flags

**Row 7 is the most important row in this table.** The work-pattern data is not collected for a
separate purpose — it falls out of version management and timestamps, which are collected for
legitimate operational reasons. But it is *available* as a behavioural profile of an identifiable
employee, and no technical or contractual control prevents it from being used that way.

Under GDPR Article 5(1)(b), further processing must be compatible with the original purpose.
Employee performance monitoring from design-tool usage data is not compatible with "version
management." The risk is not that we intend this use — we do not. The risk is that a deployer
(the OEM) could, and that we have built the raw material without restricting it.

**Row 2 has a secondary flag.** The designer's typed questions are collected to power inference.
Whether the LLM API provider retains or uses that data for model improvement is governed by their
terms. If they do, the purpose has changed without the data subject's knowledge, and we are the
party who sent the data. I have not verified the current state of OpenAI's data-use policy for
API inputs — this is flagged for review.

## Retention

Every row says "Undefined." This is not an oversight in the table — it is the actual state. No
retention period has been set for any category. Thread history, version logs, and recipient names
persist indefinitely until someone manually deletes them. This fails Article 5(1)(e) (storage
limitation) on its face.
